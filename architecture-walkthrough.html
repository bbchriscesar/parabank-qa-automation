2. Architectural Layers (Bottom → Top)

2.1 Utilities Layer

src/utils/helpers.ts

Pure functions with zero side-effects:

  • randomString(length) — alphanumeric random strings
  • randomDigits(length) — numeric-only random strings (phone, SSN, zip)
  • formatCurrency(amount) — consistent $X.XX formatting
🎤 Interview angle: Keeps test data generation deterministic in structure but unique per run, avoiding "username already exists" collisions on ParaBank's shared database.

2.2 Data Layer

src/data/user.data.ts + src/data/constants.ts

Key patterns applied:

  • TypeScript interfaces (UserRegistrationData, BillPayeeInfo) provide compile-time contracts for test data shapes
  • Factory function generateUserData() creates a fresh, unique user on every call — guarantees test idempotency
  • Constants object centralises URLs, amounts, and default payee data — single source of truth
🎤 Interview angle: "Why not hardcoded strings or a JSON fixture file?" → Uniqueness per run is required because ParaBank's database is shared/public. A static JSON would cause username collisions.

Methods provided:

  • registerUser(user, page) — Hybrid: navigates browser to establish session, then POSTs form data via page.request
  • findTransactionsByAmount(accountId, amount) — REST GET with session-aware context fallback
  • getAllTransactions(accountId) — REST GET
  • expectTransactionsExist(accountId) — Assertion wrapper; validates & returns first transaction amount

  • getAccountDetails(accountId) — REST GET
🎤 Interview angle: "Why accept both request and page?" → Enables dual-context testing: pure API tests use isolated request, while UI+API hybrid tests use page.request to share the browser session (cookies).

2.5 Custom Fixtures Layer

src/fixtures/parabank.fixtures.ts

Extends Playwright's base.test with typed fixtures. Tests import test and expect from this file instead of from @playwright/test.

export const test = base.extend<ParaBankFixtures>({
    loginPage:   async ({ page }, use) => { await use(new LoginPage(page)); },
    paraBankAPI: async ({ request, page }, use) => { await use(new ParaBankAPI(request, page)); },
    // ... 5 more page object fixtures
});

Fixtures vs. beforeEach — Why It Matters

beforeEach ApproachFixture Approach ✅
All page objects instantiated every testLazy — only created if the test destructures it
Shared state risk between testsPlaywright manages lifecycle per-test → isolation
Setup/teardown scattered in test filesEncapsulated inside the fixture definition
Harder to compose for complex scenariosFixtures can depend on other fixtures declaratively

5. 🎤 Potential Interview Questions & Answers

Architecture
Q1: "Why did you choose the Page Object Model?"
Separation of concerns. Locators and page-specific actions live in page classes, while tests remain declarative and read like user stories. If a UI element changes (e.g., a selector update), you fix it in one place — the page object — not across 20 test files.
Architecture
Q2: "Why use inheritance with BasePage instead of composition?"
DRY principle. All pages share header, sidebar, and footer navigation elements. Inheritance eliminates duplicating those 15+ locators across 7 page classes. Composition could also work, but inheritance is simpler here since every page truly "is-a" page with shared navigation — it's not forced polymorphism.
Architecture
Q3: "Why custom Playwright fixtures over beforeEach?"
Three reasons: (1) Lazy initialization — fixtures are only created if the test destructures them, saving memory. (2) Isolation — Playwright manages the lifecycle per-test, preventing shared state leakage. (3) Encapsulation — setup/teardown logic stays in the fixture definition, keeping test files clean.
Architecture
Q4: "Why a single long test instead of multiple small tests?"
State dependency chain. This test simulates a complete user journey: registration → login → account creation → transactions. Each step depends on the previous (e.g., you need the savings account number to transfer funds). Splitting would require duplicating expensive setup (registration + login) in every test, or using API shortcuts that defeat the purpose of E2E validation.
Hybrid UI + API
Q5: "Explain the dual-context API pattern with page.request vs request."
page.request shares the browser's cookies and session, so API calls are authenticated as the logged-in UI user. The standalone request is isolated and stateless. The ParaBankAPI class checks this.page ? this.page.request : this.request, enabling it to work in both UI-coupled and pure API test contexts without code duplication.
Hybrid UI + API
Q6: "Why validate transaction data via API instead of the UI?"
Speed + reliability. UI assertions on transaction tables can be flaky (pagination, rendering delays, AJAX timing). The API gives raw JSON data instantly. We leverage the active browser session via page.request so the API call is authenticated — getting the best of both worlds.
CI / Reliability
Q7: "How do you handle flaky tests?"
Multi-layered approach: (1) retries: 2 in CI auto-retries failures. (2) trace: 'on-first-retry' captures a Playwright trace on the retry attempt for debugging. (3) The JSON reporter + email script explicitly flags flaky tests (passed on retry) in the report. (4) Sequential execution (workers: 1) eliminates parallelism-induced flakiness.
CI / Reliability
Q8: "Why fullyParallel: false and workers: 1?"
Context-aware decision. ParaBank is a shared public demo server with an unoptimized database. Parallel tests cause race conditions (e.g., locking accounts, data collisions). In an enterprise environment with isolated test databases or test data management, this would absolutely be true with multiple workers.
CI / Reliability
Q9: "Walk me through your CI/CD reporting strategy."
Three-format reporter: (1) list for real-time console output during CI. (2) html for a rich visual report uploaded as a GitHub artifact (30-day retention). (3) json which is parsed by generate-email-report.js to build a structured email sent via Resend API. The email includes pass/fail counts, error messages, attachment links, and flaky/retry summaries. The email step runs with if: always() so reports are sent even on failure.
Data Management
Q10: "How do you ensure test idempotency?"
generateUserData() creates a unique user per run with a randomised username (e.g., parauser849271635), SSN, phone, and zip code. No hardcoded users. This means the test can run 1,000 times against the same environment without "Username already exists" errors. Combined with clearCookies() between registration and login, each run is fully self-contained.
